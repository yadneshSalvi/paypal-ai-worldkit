# Living Repair

The Repair workshop follows a saved market incident through the affected kit, sourced alternatives, critical-fact verification, an immutable amendment and a separately authorized controlled merchant change. A merchant switch preserves the exact engineering profile; a different model remaps its ports, clears inherited operating settings and rechecks the whole technical promise. Every affected position of the same product is included. Owned equipment and the original hard brief remain fixed.

Open **Living kit → Repair workshop**. An explicit Sample scenario creates a separate synthetic kit branch with its own merchant commitment. It does not overwrite the workbench, source reviews, inventory or live catalog. The initial commitment has test prices, zero test tax/shipping and no assumed base payment. Its synthetic assertions are not manufacturer or human-review evidence.

## Follow the workflow

1. Start **Keep the recording going**, then continue the persisted discovery checks. Inspect the same-product retailer alternative or a different exact model.
2. Save a proposal. Its before/after bundles, affected requirements, exact offers, source checks, controlled quote and digest are immutable.
3. Review one exact Sample approval, or explicitly grant a fresh automatic kit allowance. A qualifying saved proposal can execute after that allowance is saved. The allowance binds this commitment, WorldKit Studio, the displayed retailers, equipment categories and conditions, expiry, fulfillment state and current payment consent.
4. A $25 allowance can cover the $8 change. **Try the next $20 change** starts another labelled Sample observation on the same commitment; $8 + $20 exceeds that original allowance. A refund does not restore it. An unavailable wallet within the cap asks for payment approval; a genuine cap failure asks for new consent.
5. After commitment, **Review conditional undo → Check current restoration** reads original exact stock, current cost, technical facts and the eligible capture balance. Review the separate compensation consent before any refund or restoration. A higher current restoration cost requires a fresh supplemental buyer approval.

Other Sample scenarios cover open critical evidence, an over-cap change, unavailable original equipment, simulated shipment, a lost capture response and a paid change that cannot be committed. Shipment simulation is restricted to the Sample branch and ends automatic authority and undo eligibility. A private support request is a saved workspace record; it sends no external message.

## Payment and evidence boundaries

Channel3 supplies product and offer observations. It does not place retailer orders, reserve stock, ship equipment or issue retailer refunds in this workflow. WorldKit Studio is the controlled demonstration merchant. Real retailer shipping and landed costs remain unknown and separate from its test quote.

The existing digital dossier's $12 checkout, $8 example and retired policy do not authorize a kit amendment. A new kit policy uses `controlled_kit_amendments`; fresh buyer approval is the other path. Source-level PayPal sandbox execution uses the installed guarded core and existing SDK adapter. Actual sandbox qualification of this new scope remains a separate release step. Connecting a wallet, discovering an alternative, a model proposal or an MCP result alone grants no financial authority.

The durable Sample payment provider has no network client or financial credentials. Its receipts say `sample` and `local_fixture`. A real catalog proposal cannot use it. A Sample premise cannot satisfy the live manufacturer-source/reviewer gate. Replays grant no payment authority.

## Persistence and recovery

Ten additive tables hold repair runs, candidates, current and historical commitments, immutable amendment proposals, kit policies, gross claims, compensation requests, the in-app outbox and Sample payment receipts. Existing domain and guarded-core tables retain financial authorities, operations and owned resources. `npm run db:migrate` initializes the complete additive schema; migration makes no provider call. Use only the intended project's database or an isolated test schema.

Workers use bounded discovery steps, leases and fenced completion. Equivalent observations on the same kit/commitment version share a repair cause. A current in-stock read resolves an earlier shortage. Later events reuse the exact current commitment; already changed retailers and fulfilled lines cannot restart an old authority. Stopping discovery invalidates its lease.

Consent and gross claims persist before dispatch. An interrupted dispatch resumes the same encrypted command and provider request identity. Unknown create/capture/refund results reconcile the original operation and retain their reservation. Refund attribution rereads one owned capture, its order and every known individual refund; pending, stale, ambiguous or conflicting evidence blocks another refund. A newer unresolved payment observation also pauses restoration.

Commitment and graph changes are atomic. A completed payment followed by an uncommittable change requires separate compensation. A completed refund followed by failed restoration remains recorded with `partial_support_needed`. Historical graph versions and gross charges never disappear. Read-only reconciliation can continue after browser expiry or policy revocation; fresh dispatch cannot.

The read API returns recent run summaries and the selected run's complete evidence, preserving old exact links without retransmitting every historical graph. Gross allowance calculations include all claims for the selected commitment. PayPal returns open their exact amendment rather than the legacy digital-service screen.

## Verification

Local validation uses an isolated PostgreSQL schema, an isolated production export on port 4506 and empty provider credentials. Run unit checks with `npm test`; run database checks only against a dedicated test database/schema, for example `node --env-file=<private-test-env> --import tsx --test --test-concurrency=1 tests/*.integration.ts`. TypeScript and a production build are also required.

The local record covers the complete Sample payment/commitment/refund/restoration journey, cumulative and concurrent caps, expiry/revocation, lost responses, partial prior refunds, failed restoration, source/tenant boundaries, multi-position changes, event continuity and bounded history reads. Native mobile review covers the committed and restored states at 390 pixels. These observations do not establish authentic market delivery, actual new-scope sandbox money movement, manufacturer accuracy, independent engineering review or physical compatibility. Those gates remain open.
