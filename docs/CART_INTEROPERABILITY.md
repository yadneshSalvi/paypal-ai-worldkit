# Merchant cart interoperability

This unit implements the public merchant Cart API boundary independently of Store Sync enrollment. The current WorldKit Studio digital service is not eligible for Store Sync and is not relabeled as physical goods. The interactive qualification environment uses a separate, explicitly Sample physical-merchant catalogue, stock, shipping, buyer approval and settlement ledger. It sends no financial or retailer request and promises no shipment.

The persistent merchant interface and complete Sample workbench are implemented. All 85 affected checks pass locally: seventeen contract/authentication checks, twenty-two real React/DOM interaction checks and forty-six database/HTTP checks. The totals include independently authored adversarial tests. Native, production-runtime and hosted qualification are separate results; this document does not claim those checks before they run.

## Verified public contract

The source of request/response types, validation schemas and the conformance client is the published Apache-2.0 package [`@paypal/agentic-commerce-spec@1.1.0`](https://www.npmjs.com/package/@paypal/agentic-commerce-spec). Its generated `src/generated/types.gen.ts`, `zod.gen.ts` and `sdk.gen.ts` were inspected on 12 November 2026. The package's README contains older examples; generated operation names and schemas are authoritative for this pinned implementation.

| Operation | Request | Successful response | Semantics |
| --- | --- | --- | --- |
| `POST /merchant-cart` | `PayPalCartWritable`, bearer authorization, JSON | 201 `PayPalCart` | New merchant-owned cart; incomplete business data remains visible in validation issues |
| `GET /merchant-cart/{cartId}` | Bearer authorization; exact cart ID | 200 `PayPalCart` | Current cart or retained completed receipt |
| `PUT /merchant-cart/{cartId}` | `PayPalCartWritable`, bearer authorization, JSON | 200 `PayPalCart` | Complete replacement; omitted customer/address/selection fields are removed |
| `POST /merchant-cart/{cartId}/checkout` | `PayPalCartWritable`, bearer authorization, JSON | 200 `PayPalCart` plus optional payment confirmation | Exact owned token, buyer approval, current cart/quote/graph and durable settlement required |

Technical errors use the generated `errorSchema`; business refusal uses `businessErrorSchema` and HTTP 422. Incoming calculated top-level fields are rejected. Item prices, names and shipping amounts never override merchant records. All amounts use integer minor units internally and generated `Money` objects at the boundary.

The [official Postman collection](https://www.postman.com/paypal/paypal-agentic-commerce-workspace/collection/52882817-309b7569-7530-41fc-8be0-82f96c7d3f11/paypal-agentic-commerce) documents merchant-hosted paths, complete checkout, RS256, `iss: paypal.com`, merchant `sub`, platform-domain `aud`, `cart`/`checkout` scopes, external PayPal-account identity and self-signed lower-environment tokens. It sets endpoint targets of three seconds for create/read/update and five for checkout. One local run recorded 83 loopback HTTP responses: maximum create 15.14 ms, read 6.41 ms, replace 8.61 ms and checkout 15.65 ms. Those are controlled local transport measurements, including refusals; they establish no hosted latency or genuine provider delivery. The linked OpenAPI website returned 404 during this audit, so no missing contract was filled from memory.

The APIMatic TypeScript skill's scope guard is the separate `paypal` package and `PaypalClient`. This cart boundary introduces no APIMatic client or financial SDK operation. Any later actual payment adapter must first extend the existing root `paypal-plan.md` contract and follow that skill, current application authority and root-owned provider qualification.

## Authority and persistent state

- Each Sample merchant and catalogue belongs to one active private workspace. A catalogue line references an immutable saved system edition and its exact graph hash. Channel3 search results never become merchant inventory or fulfillment authority.
- An integration credential binds one merchant, issuer, audience, external account identity, allowed scopes, expiry and a pinned RSA public key. The private key is not persisted or returned. A signed token is shown once; current credential revocation and original session expiry are checked on every operation.
- Only a configured public key is used. Request-controlled `jwk`, `jku`, `x5u`, algorithms or hosts cannot select verification material. Missing or foreign authority fails before cart lookup.
- Cart revisions and command receipts are durable. A caller may provide the documented WorldKit `Idempotency-Key` extension; this is not represented as a PayPal requirement. An identical retry returns the original response; reuse for a different operation or payload fails. Without the extension, POST creates a distinct cart, while checkout remains unique per cart and approved quote.
- The browser journals a Sample command in tab session storage before transport, bound to an opaque workspace identity. A lost response retains the exact command across navigation/reload and blocks other mutations. Recovery is explicit; mounting or refreshing never redispatches it. A known success followed by a failed refresh only requires a read. One-time integration credentials are never put in this journal.
- PUT replaces the complete writable document and invalidates old approval/payment identity when that document changes, even if the merchant-calculated amount is unchanged. Omitted caller fields cannot survive because a normalized quote happens to match. Updates after completion are refused. Concurrent checkout attempts cannot create duplicate settlement or completion records.
- Current stock, prices, source edition, session, merchant and credential are rechecked before completion. A stale graph, changed price, unavailable stock, expired approval or foreign token produces a concrete recoverable refusal. An earlier receipt remains in history.
- Approval expiry is checked again after current system proof is available and after the pending effects. A regression held the actual project lock and advanced the controlled application clock after checkout read the approval; the corrected operation retains a refusal with no settlement or stock change. This controlled test is not an actual payment or wall-clock expiry observation.
- Sample approval is explicit and binds this exact cart revision, graph, quantity, amount and token. The simulated settlement is durably recorded as Sample. It never produces a genuine PayPal receipt, a retailer order or a fulfillment claim.

## Complete local workflow

Open **Cart lab** and deliberately start its separate Sample merchant. Add an exact saved desk or podcast system, entering an example unit price and local stock count. Create a complete cart with fictional buyer/address details, review its server-calculated USD amount and approve that exact version. Completing it records one Sample settlement and adjusts only local Sample stock. The downloadable dossier retains the saved cart, catalogue proof and activity with zero real funds, equipment orders or fulfillment.

Changing a merchant price or stock removes current approval. The interface keeps the saved quote with its original version/hash and shows a changed current merchant amount separately until a reviewed replacement is saved. Current and historical versions have deliberate focus targets, retained totals and distinct controls. Reload preserves the selected cart, historical version and reading view. Pending reads block mutations; accepting a fresh read clears earlier drafts and checked consent, so a different version or workspace cannot inherit them. The scope selector cannot give an integration client buyer approval authority. A one-time credential is masked, can be deliberately copied, disappears on close and has an immediate revocation control.

The seventeen primary DOM checks exercise actual component events, pending controls, modal focus/Escape return, exact second-system selection, explicit buyer consent, changed-quote rendering, historical controls/reload, cleared replacement fields, unsupported country preservation, credential scope/revocation, keyboard tabs, uncertain response recovery, workspace isolation and unavailable/corrupt recovery storage. Five independent DOM checks cover refresh/consent races, foreign-workspace drafts, late responses, explicit remount recovery and read-only expiry handling. Their HTTP responses are synthetic.

The twenty-eight primary database checks use the official generated Axios client over a real local HTTP listener, actual handler code and an isolated PostgreSQL cluster. They cover process restart, immutable rows, current authority after lock wait, response schemas, multiple merchants, complete replacement, replay/collision, duplicate/concurrent checkout and independent source/stock/price changes. Eighteen independent database/HTTP checks add socket-destroyed post-commit recovery, full PUT omissions, actor/key isolation, queued revocation, stock-only drift, rollback after pending writes, current merchant authority and streamed size/UTF-8 boundaries. First failures and their corrected results are retained in private qualification evidence.

## Remaining external gates

[Store Sync's documented eligibility](https://developer.paypal.com/store-sync/overview) is physical goods sold to US customers in USD, with merchant onboarding and access. WorldKit has not established those conditions. Actual PayPal-signed keys, program registration, a genuine merchant catalogue, taxes/shipping/returns, provider execution, retry/delivery behavior and real order fulfillment remain separate root-owned gates. The existing digital verification/support checkout stays separate.

Production Next.js transport, independent native presentation and any hosted deployment remain separate acceptance steps. The local test suite creates fresh controlled workspaces and never renews protected original sessions or alters their graphs, payment history or fixed expiry.
